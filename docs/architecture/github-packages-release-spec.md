# GitHub Packages release architecture specification

**Project:** XQ Test Platform  
**Status:** Implemented architecture contract; first Changesets-managed release still requires maintainer approval  
**Release strategy:** Lockstep Semantic Versioning  
**Registry:** Private GitHub Packages npm registry  
**Package scope:** `@experiencequality`

## 1. Purpose

This document defines the package management and release architecture for the XQ Platform monorepo. It adapts the approved release model to the repository's actual structure rather than requiring the example directory layout from generic references.

The repository is the source of truth, GitHub Packages is the distribution mechanism, Changesets is the version-management mechanism, and GitHub Actions is the release-execution mechanism.

## 2. Decisions

| Area                          | Decision                                               |
| ----------------------------- | ------------------------------------------------------ |
| Repository                    | Single Git monorepo at `ExperienceQuality/xq-platform` |
| Runtime                       | Node.js 24 or newer                                    |
| Language                      | TypeScript/ESM                                         |
| Package manager               | pnpm `12.10.0` with a committed `pnpm-lock.yaml`       |
| Workspace                     | Flat `packages/*` and private `apps/*` globs           |
| Registry                      | `https://npm.pkg.github.com`                           |
| Package scope                 | `@experiencequality/*`                                 |
| Registry visibility           | Private/restricted                                     |
| Versioning                    | Lockstep SemVer through one Changesets `fixed` group   |
| Release approval              | Merge of the generated Version Packages PR             |
| Publication                   | `publish.yml` only; no developer manual publication    |
| Release identity              | One `vMAJOR.MINOR.PATCH` platform tag/GitHub Release   |
| Changelog                     | Per-package `CHANGELOG.md` generated by Changesets     |
| Report and skills publication | Separate workflows; not Node package releases          |


| Directory            | Responsibility                                                     |
| -------------------- | ------------------------------------------------------------------ |
| `packages/`          | Exactly the seven approved publishable product packages            |
| `apps/`              | Private showcase and E2E consumers; never published                |
| `scripts/`           | Structure, archive, registry, release, and platform-release checks |
| `.changeset/`        | Pending release intent and fixed-group configuration               |
| `.github/workflows/` | Build/Test validation and Node release automation                  |
| `docs/`              | Consumer, development, release, and architecture documentation     |

The root package and all workspaces under `apps/` remain `"private": true`. Only the explicit package inventory may publish.

## 4. Package naming and inventory

All publishable packages use the organization scope and lowercase kebab-case:

1. `@experiencequality/rest-client`
2. `@experiencequality/db`
3. `@experiencequality/stub`
4. `@experiencequality/core`
5. `@experiencequality/test`
6. `@experiencequality/test-browser`
7. `@experiencequality/test-infra`

`xq-infra` is the executable provided by `test-infra`, not an eighth package. The canonical inventory lives in `scripts/publishable-packages.mjs`; adding a publishable package requires updating that inventory, the Changesets fixed group, the package-boundary map, and the repository documentation.

## 5. Lockstep versioning

All seven packages share one exact `MAJOR.MINOR.PATCH` value. Changesets owns version preparation and changelog generation through `.changeset/config.json`:

- `fixed` explicitly lists all seven packages.
- `access` is `restricted`.
- `baseBranch` is `main`.
- `privatePackages.version` and `privatePackages.tag` are false.
- `updateInternalDependencies` is `patch`.
- `changedFilePatterns` limits the required changeset check to package source/config/manifest files so documentation-only package edits do not force a release.

When multiple changesets request different increments, Changesets selects the highest increment for the whole group. The first managed platform release is intended to be `1.0.5`, subject to maintainer approval and live workflow verification.

## 6. Publishable package contract

Every publishable package must have:

- A unique approved `@experiencequality/<kebab-name>` package name.
- The shared exact version.
- `"type": "module"`.
- Node engine `>=24`.
- A `build` script producing package-local `dist/`.
- A `test` script.
- A `files` list containing `dist` and `package.json`.
- `publishConfig.registry` set to `https://npm.pkg.github.com`.
- Either a typed `exports["."]` entrypoint or an explicit CLI `bin` mapping.
- Internal dependencies expressed as `workspace:*` in source manifests.
- A `repository.url` pointing to `ExperienceQuality/xq-platform` and a `repository.directory` matching its package path.

Packed artifacts must contain ordinary aligned dependency versions and no unresolved `workspace:` references. `test-infra` intentionally ships only the compiled `xq-infra` CLI; it does not expose a public module entrypoint.

## 7. Authentication

GitHub Actions uses the repository `GITHUB_TOKEN` with job-scoped permissions. Publication requires `packages: write`; registry verification requires `packages: read`; platform tag/release creation requires `contents: write`; Version Packages PR creation requires `contents: write` and `pull-requests: write`.

Developers and consumers use an environment-provided GitHub token with `read:packages`. Local/consumer `.npmrc` configuration routes only the organization scope:

```ini
@experiencequality:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GH_PACKAGES_TOKEN}
```

For a consumer repository's GitHub Actions workflow, grant that repository access through each package's GitHub Package settings and use its `GITHUB_TOKEN` or another approved read-only credential. No token belongs in source control.

## 8. Release lifecycle

```text
Feature PR + required changeset
  -> Build/Test validation
  -> merge to main
  -> Changesets version mode creates or updates Version Packages PR
  -> maintainer reviews version, changelog, and lockfile changes
  -> maintainer manually dispatches Build/Test on the release branch
  -> merge release PR to main
  -> exact SHA Build + Test + ci:release gate
  -> pack -> publish -> verify all seven registry versions
  -> create one platform tag and GitHub Release
```

A manual tag does not initiate publication. A release is not successful until every expected package/version is visible in GitHub Packages and the single platform release record exists. Partial publication is retried only from the same immutable `release_sha`; metadata-only recovery uses `finalize_only: true`. Existing package versions and tags are never overwritten or retargeted.

## 9. Validation requirements

Pull requests must satisfy the existing Build and Test matrix checks. Package source/config/manifest changes must include a changeset unless the change is documentation-only or the PR is the generated release branch.

Publication requires all of:

- `pnpm run check`
- `pnpm test`
- `pnpm run test:release`
- Packed-consumer verification through `pnpm run verify:packages`
- Cucumber report verification
- Backend Docker E2E
- Browser Playwright E2E
- Real-Docker infra E2E through `pnpm run test:e2e:infra`
- Exact-version registry reconciliation for all seven packages

## 10. Consumer contract

Consumers install explicit platform versions and keep all `@experiencequality/*` dependencies on the same version:

```json
{
  "dependencies": {
    "@experiencequality/test": "1.0.5",
    "@experiencequality/test-browser": "1.0.5",
    "@experiencequality/test-infra": "1.0.5"
  }
}
```

Production consumers pin exact versions rather than wildcards. Operational installation details live in `../consumer-guide.md`; operational retry and ownership rules live in `../release-policy.md`.
